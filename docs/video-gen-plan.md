# 自动生成视频方案（待审阅）

> 状态：**方案稿，未实施**。审阅确认后再动手。
> 目标：每周/每月自动把监测数据（仪表盘图表 + Top 数据）生成一支 1080p 数据周报视频（MP4），
> 可手动查看或进一步投稿。

## 视频形态设想

一支 30~60 秒的"数据周报"短片，例如：

1. **片头（2s）**：标题卡 "B站官号数据周报 · 2026-W34"，品牌色渐变背景
2. **总览（5s）**：本周视频数 / 累计播放 / 播放增量 大数字动画
3. **图表展示（各 6-8s）**：周报四宫格各子图依次入场，Ken Burns 缓推/平移，
   关键数字（如本周增量最大账号）高亮
4. **Top 榜滚动（10-15s）**：Top15 标题+播放量逐条浮现或滚动条动画
5. **片尾（2s）**：生成时间 + "数据来自本地监测系统"

输出：1920×1080 / 30fps / MP4（H.264），竖版 1080×1920 可作为二期。

## 方案 A：Python + FFmpeg/moviepy（推荐）

架构：新增 `bmon/video.py` + `main.py video` 子命令，纯 Python 本地生成。

```
videos_with_stats / snapshots (SQLite)
   → 数据脚本(本期增量/Top榜/总览数字)
   → charts.py 出图(已有) + Pillow 生成标题卡/Top条幕
   → moviepy 合成: 图片序列 + 转场 + Ken Burns 缩放 + BGM
   → ffmpeg 编码 → output/videos/weekly_2026-W34.mp4
```

**技术选型**
- `moviepy>=2.0`（或直接用 FFmpeg 滤镜链，零 Python 依赖但脚本复杂）
- 数字滚动动画：Pillow 逐帧渲染或用 moviepy TextClip
- 转场：交叉淡入即可，够用且稳定
- 依赖增量：`moviepy`、`pillow`、`numpy`、ffmpeg（moviepy 自带 imageio-ffmpeg）

**实现要点**
- 数据层直接复用 `Database.videos_with_stats()` 与 `snapshot_report()`，
  与图表同源，保证视频数字与 PNG 一致
- 模板化：`config.yaml` 新增 `video:` 段（分辨率、BGM 路径、片头文案、时长）
- 与现有流程衔接：`run_loop` 每轮出图后可选自动出视频；
  或计划任务每日采集后仅周一/每月 1 号生成周/月报视频

**优点**：与现有技术栈一致（纯 Python）；无网络依赖；可完全自动化；易调试。
**缺点**：动效上限一般（复杂粒子/弹性动画吃力）；moviepy 渲染速度中等
（30-60s 视频预计渲染 1-3 分钟）。

## 方案 B：Remotion（React 程序化视频）

架构：React 组件写视频（每一帧都是 DOM），`npx remotion render` 输出 MP4。

- 动效能力上限高（CSS/JS 动画、弹性曲线、SVG），适合做出"高级感"数据可视化短片
- 数据注入：Python 侧生成 JSON 数据文件，Remotion 组件读取渲染
- 缺点：引入 Node.js 依赖链（npm 包体积大）；学习/维护成本高于方案 A；
  本机需安装 Node 与 headless Chrome

**适用**：对视觉效果要求高、愿意维护一套前端模板时的二期升级路线。

## 方案 C：纯 FFmpeg 幻灯片（最简兜底）

一条命令把 PNG 序列拼成带淡入淡出的视频：

```bash
ffmpeg -framerate 1/6 -i slide_%d.png -vf "fade=t=in:st=0:d=1" \
       -c:v libx264 -pix_fmt yuv420p out.mp4
```

**优点**：零依赖、十分钟可用。**缺点**：没有数字动画与排版自由度，观感朴素。
可作为方案 A 落地前的快速原型。

## 可选扩展：自动投稿 B站

- 技术上可用登录态 Cookie + 投稿接口（bilibili-toolman / biliup 等开源工具）自动上传
- **风险提醒**：自动投稿需要账号登录态，与本项目"零登录、游客采集"的安全设计相悖；
  建议作为独立的手动步骤（生成后人工投稿），不纳入自动流水线
- biliup 支持定时、多 P、简介模板，若决定做可单独评估

## 方案对比

| 维度 | A moviepy | B Remotion | C 纯 FFmpeg |
|---|---|---|---|
| 动效上限 | 中 | 高 | 低 |
| 依赖 | Python 包 | Node + Chrome | 仅 ffmpeg |
| 开发工作量 | 中（约 2-3 天） | 大（约 1 周+） | 极小 |
| 自动化衔接 | 原生（同进程） | 需跨进程调用 | 脚本拼接 |
| 渲染速度 | 中 | 慢 | 快 |

## 推荐结论

- **一期：方案 A（moviepy）**——与现有 Python 架构无缝衔接，先实现"自动生成可用"的周报视频
- 视觉不满足时**二期升级方案 B**，数据层与文案层可完全复用
- 方案 C 可在一期开发期间当临时兜底
